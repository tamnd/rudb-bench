A number that was true on the day it was measured stays in the directory even after a faster one exists, because a history that overwrites itself is a table rather than a history, and the interesting question is usually what changed between two of these rather than what the latest one says.

A ladder is one measurement rather than three or four, and the sizes are meant to be read together. A single size cannot tell a fixed cost apart from a per row cost, and which of the two an engine is paying is usually the only thing worth knowing about it. See the top of the [README](../README.md) for what these ladders say.

There are ladders from two machines here, and rule seven says a number from one machine is never compared against a number from another. `gamingpc-wsl` has 32 hardware threads and now reaches the whole hundred million row file. `vmi3391933` has 8 and stops at a hundred thousand. Reading a row off one and a row off the other is the mistake the rule exists to prevent.

The four files with `quiet` in the name are a second sweep of the same ladder on `gamingpc-wsl`, taken a few hours after the first. Every engine in them started with the one minute load average under four on a machine with 32 threads, which each report records per engine. The first sweep ran while another agent was building DuckDB from source on the same box, and reading the two against each other is the interesting thing in this directory right now: contention cost DuckDB roughly three times its query time at a million rows and cost rudb less than twice, because DuckDB was trying to use three and a half cores and rudb was using one. The busy sweep is kept rather than replaced, both because runs are always kept and because it is the evidence for that.

`run-clickbench-server3.md` is the odd one out and is kept because runs are kept. It predates rudb running the suite at all, so it is DuckDB against DataFusion and nothing else, and its file name says `server3` where the later ones say the host name the machine actually answers to.

`run-clickbench-gamingpc-wsl-100m.md` is the first run in this directory against the real `hits` rather than a strided sample of it, all 99,997,497 rows and 13.76 GiB, six engines, nothing capped. It is the only file here without a sampling caveat, and reading it against `run-clickbench-gamingpc-wsl-10m.md` is what the ladder is for: the 10m file was written by the harness at `ROW_GROUP_SIZE 8192` and has 1204 row groups, where the real file has 226 of about 442,000 rows each, so the sample has five times the row groups of the file ten times its size. rudb's floor turned out to track row groups rather than rows, which is why its `COUNT(*)` is faster on the full file than on the tenth of it. That is a bias in how the harness writes samples rather than a fact about any engine, and it is written up at the top of the [README](../README.md).

`run-clickbench-gamingpc-wsl-100m-tmpfs-scratch.md` has three of its six engines missing and is kept because runs are kept, including the ones that were the measurer's fault. DuckDB and the pinned DuckDB exited without a word and `clickhouse-local` said `NOT_ENOUGH_SPACE`. The harness puts its scratch directory under `std::env::temp_dir()`, and `/tmp` on `gamingpc-wsl` is a 16 GB tmpfs, so the three engines that load into a format of their own were writing a 25 GiB database into the RAM of a 31 GiB machine. `RUDB_BENCH_SCRATCH` pointed at real disk is the fix and the file above is the rerun. It is worth keeping because an engine that dies silently at one size and not at the smaller ones is very easy to write up as an engine that cannot do the work. Its first commit also carries the subject of the commit after it, which is wrong and is left alone rather than rewritten under an open pull request.

`run-tpch-gamingpc-wsl.md` is the first TPC-H run in this directory that asked rudb, and rudb has no column in it. The harness declined to time it rather than timing it badly: every join in rudb is still a nested loop and the suite is twenty two join plans, so the number would have been a hang. That abstention is recorded in the engines table of the report with its reason and its milestone, which is the form these are supposed to take. Its corpus is a fresh `dbgen` at SF100, 33.20 GiB of Snappy Parquet in eight tables with `lineitem` at exactly 600,037,902 rows, written at DuckDB's default row group size for the reason in the paragraph above. It is a different corpus from the one behind the `2a` row of `runs/tpch.txt`, which was 22.50 GiB, so the two are beside each other rather than one replacing the other. Polars has no column either, and that one is an out of memory kill: `dmesg` has the run's `python3` going down at 29.4 GiB on a 31.34 GiB machine, and two reruns since did the same. The report's own sentence about it blames a `DeprecationWarning`, which is wrong and is the harness's fault rather than the reader's: an OOM kill leaves nothing on stderr, so the wrapper quoted the last six lines it could find and those were the warning. `both` in `src/data.rs` should say when an exit was a signal instead.

The two runs under `2026-09-17` are the first with `clickhouse-server` in them, next to `clickhouse-local`, DuckDB and Polars, and they have no rudb column because that box has no rudb at a current version on it. They also say `server3-1m` and `server3-100k` in their machine field rather than `vmi3391933`, because `RUDB_BENCH_MACHINE` was set on the way in so that the two would not write over each other. The host table inside each of them still reads the real host name off the machine. What they are for is written up in [three engines under the official driver](2026-09-17/official-driver-ladder.md), which is the other half of the same afternoon.
